이번 승인과 산출물의 범위
승인된 7개 화면 시안을 구현 가능한 작업 단위로 정리한다. 현재 단계는 계획서 작성이며, 저장소 수정·PR 생성·배포는 수행하지 않았다. 시안의 예시 대화·분석 수치·모델·연결 상태는 실제 서비스에 하드코딩하지 않는다.

1. 목표와 완료 상태

  • 따뜻한 배경, 인디고색 주요 행동, 학생·교사·멘토 구분, 넉넉한 여백을 전체 화면에 일관되게 적용한다.
  • 교사는 시나리오 선택 → 대화 → 종료 → 분석·근거 확인 흐름을 명확하게 이해할 수 있어야 한다.
  • 관리자는 시나리오 작성, 공통 모델 설정, 동일 맥락 비교, 제공자·모델 검증을 기존 기능 그대로 수행할 수 있어야 한다.
  • FastAPI·Jinja2·HTMX·기존 JavaScript 구조를 유지한다. React 전환, 데이터베이스 마이그레이션, AI 정책 변경은 이번 작업에 포함하지 않는다.
  • 승인 시안의 화면 탐색 메뉴는 검토용이다. 실제 서비스에서는 진행 중인 세션이 있어야 대화에, 분석 대상이 있어야 결과에 접근하도록 기존 경로와 상태를 유지한다.

현재 확인 수준:저장소 템플릿·스타일·브라우저 테스트 실행 구조와 참고 사이트 HTML/CSS를 확인했다. 승인 시안의 JavaScript 문법 검사는 통과했으나 Chromium 실행 파일 부재로 브라우저 동작·반응형 검증은 완료하지 못했다. 시각적 승인과 기능 검증 통과를 구분하며, 구현 전 브라우저 검증 환경부터 준비한다.

4. 단계별 작업 계획

단계 0 · 기준 확정과 실행 환경

  • 구현 시작 시 원격 main의 최신 커밋을 확인하고 ffa0046 이후 변경을 대조한다. 변경된 템플릿·테스트가 있으면 이 계획의 대상 경로를 갱신한다.
  • 작업 브랜치 feat/premta-ui-refresh를 만들고 현재 화면 및 역할별 메뉴를 기록한다.
  • README 기준으로 의존성과 Chromium을 설치한다. 임시 DB·합성 데이터·모의 제공자 응답으로 테스트한다.
  • CSS/DOM에 연결된 ID, data-*, hx-*, 폼 필드명, 이벤트 위임 선택자를 확인한다.

완료 기준:기존 화면이 테스트 환경에서 실행되고, 기준 테스트 실패가 있다면 변경 전 문제로 구분해 기록한다.

단계 1 · 공통 디자인과 탐색 구조

  • 기존 CSS의 의미 기반 변수를 재사용하여 팔레트·간격·서체·역할·상태 토큰을 정리한다.
  • 헤더, 메뉴, 입력 폼, 주요·보조 버튼, 오류 안내, 알림, 모달, 표에 공통 규칙을 적용한다.
  • 로그인·관리자 권한에 따른 탐색 구조를 유지하고 현재 위치를 표시한다.
  • 페이지 전용 CSS를 대조하여 흑백 값·고정 폭·전역 선택자 충돌을 순차적으로 제거한다. 임시 덮어쓰기 파일과 !important를 누적하지 않는다.

완료 기준:로그인·교사·관리자 대표 화면의 공통 디자인과 모바일 메뉴가 정상 동작한다. 이후 단계는 이 토큰을 사용한다.

단계 2 · 교사 화면과 연습 흐름

  • 시나리오 카드와 소개 영역을 적용한다. 소개 영역이 실제 목록 접근을 과도하게 밀어내지 않도록 높이를 제한한다.
  • 대화 화면의 상황 정보·학생 정보·입력·멘토 도움·종료 행동을 정돈한다. 모바일에서는 기존 정보/대화 전환 흐름을 유지한다.
  • 분석 화면의 핵심 피드백과 발화 근거를 연결하고, 이력 화면과 CSV 행동을 동일한 디자인으로 정리한다.
  • 긴 대화·줄바꿈·긴 제목과 로딩·빈 상태·오류·분석 부분 결과를 점검한다.

완료 기준:모의 AI로 시나리오 선택 → 질문·응답 → 멘토 도움 → 종료 → 분석·근거 확인 → 기록 조회 흐름을 통과한다.

단계 3 · 관리자 작성·비교·연결 화면

  • 시나리오 목록·5단계 작성기를 적용한다. 입력값과 미리보기 연결, 초안 저장, 게시 전 오류 이동을 점검한다.
  • 공통 모델과 역할별 옵션의 관계를 설명하고 검증되지 않은 모델의 실행 불가 상태를 유지한다.
  • 비교 패널의 진행·완료·실패·중단·채택 상태를 구분한다. 모바일은 패널을 수직 배치하고 제공자·모델명을 반복 표시한다.
  • AI 연결 화면을 제공자 → 모델 → 역할 검증 순으로 정돈한다. 실제 키·저장·재인증 흐름은 기존 구현을 연결한다.
  • 사용자·그룹·세션·분석·사용량·소개 화면의 표, 필터, 페이지 이동, 모달에도 공통 스타일을 적용한다.

완료 기준:작성·저장·재열기·게시, 비교·채택·다음 질문·비교 종료, 제공자 설정과 역할 검증의 기존 동작이 유지된다.

단계 4 · 통합 검증·리뷰·PR

  • 승인 시안과 실제 화면의 차이를 비교한다. 실제 데이터와 기존 기능을 보존하기 위한 차이는 PR에 이유를 적는다.
  • 영향 테스트와 관련 통합 테스트를 실행하고, 공통 CSS·레이아웃 전역 변경이므로 최종 전체 브라우저 검사와 전체 pytest를 한 번 수행한다.
  • 문제를 수정한 뒤 실패·영향 범위만 재검증한다. 변경 없는 전체 검사를 반복하지 않는다.
  • 리뷰용 PR에는 핵심 7화면의 전후 비교, 모바일·다크 모드 결과, 테스트 명령·결과·미검증 항목을 첨부한다.
  • PR 리뷰와 기존 저장소의 CI·머지 정책에 따라 완료한다. 운영 적용은 별도 실행 단계로 기록한다.

진행 원칙:단계별 완료 기준을 충족한 뒤 다음 단계로 이동한다. 기본은 한 브랜치·한 PR 안에서 단계별 커밋으로 구분한다. 별도 프레임워크나 중복된 테스트 체계를 도입하지 않는다.

5. 기능 보존 계약

  1. 데이터·보안:기존 엔드포인트, CSRF, 권한 검사, 세션 소유권, 관리자 재인증, 암호화된 키 저장을 유지한다. 공개 화면에 내부 프롬프트·멘토 판단 이유·비밀키를 노출하지 않는다.
  2. 대화:학생 스트리밍과 멘토 개입을 독립적으로 표시한다. 실패·중단·새로고침 복구, 전송 잠금, 사용자의 명시적 재시도 정책을 보존한다.
  3. 시나리오:공통 모델과 역할별 옵션을 유지한다. 과거 혼합 모델 설정을 임의로 통일하거나 과거 세션의 고정 설정을 바꾸지 않는다.
  4. 비교:각 패널은 동일한 공통 대화를 사용한다. 완료된 응답 채택과 이후 공통 이력 반영, 패널별 오류·재시도·중단 정책을 보존한다. 일반 수업 기록에 비교 데이터를 섞지 않는다.
  5. 분석:새 실행 상태와 기존 채택 결과를 구분한다. 부분 결과·실패 결과가 기존 정상 결과를 덮어쓰지 않게 한다. 근거·분류·통계는 서버 검증 결과를 그대로 사용한다.
  6. 폼:입력 내용, 숨겨진 옵션, 미저장 경고, expected_version 충돌, 오류 요약·필드 이동을 유지한다. 탭 변경으로 입력값이 지워지지 않아야 한다.

단순 색상·간격 수정에 전체 TDD를 강제하지 않는다. 기존 검사를 재사용하고, 새 탭 동작·반응형 탐색·상태 변경에 새 실패 가능성이 생겼을 때만 해당 동작을 검증하는 테스트를 보강한다. 오류가 발견되면 재현 가능한 실패 사례를 먼저 확보한다.

시각·접근성 검증

  • 320·390·768·1024·1440px에서 핵심 화면을 확인한다. 문서 전체의 가로 넘침은 없어야 하며, 꼭 필요한 관리자 데이터 표만 자체 스크롤을 허용한다.
  • 일반 글자 대비 4.5:1, 큰 글자·필수 UI 경계 대비 3:1을 기준으로 확인한다. 다크 모드도 별도로 확인한다.
  • 키보드로 메뉴·탭·입력·모달·주요 행동에 접근할 수 있어야 한다. 포커스 표시·모달 닫기 후 복귀·오류 필드 안내를 유지한다.
  • 터치 행동 영역은 약 44px 이상, 입력 폰트는 16px 기준으로 유지한다. 200% 확대에서도 주요 기능이 가려지지 않아야 한다.
  • 역할과 상태는 색상뿐 아니라 텍스트로도 구분한다. 스트리밍 알림이 매 토큰마다 과도하게 읽히지 않게 한다.

7. 위험 요인과 대응

위험대응
공통 CSS가 관리자·모달까지 영향을 줌전역 토큰과 페이지별 선택자를 구분하고, 공통 단계부터 전체 템플릿 목록으로 회귀 확인한다.
레이아웃 재구성이 JS 선택자·HTMX 연결을 끊음ID·폼명·이벤트 연결을 먼저 목록화하고 유지한다. 변경이 필요한 경우 연결 코드와 테스트를 같은 커밋에서 수정한다.
시안처럼 정상 상태만 구현비어 있음·로딩·실패·중단·부분 결과·권한 제한·충돌·검증 만료 상태를 완료 기준에 포함한다.
긴 대화·비교 응답이 모바일을 밀어냄줄바꿈·고정 폭 제거·수직 배치·입력 영역 접근성을 긴 합성 데이터로 확인한다.
브라우저 검증 환경 부재단계 0에서 환경을 준비한다. 실패하면 원인과 미검증 항목을 기록하고 시각·기능 검증을 통과했다고 보고하지 않는다.
최신 main과 계획 기준 간 차이착수 시 차이를 재확인하고 기존 변경을 덮어쓰지 않는다. 변경된 계약에 맞게 작업 범위를 조정한다.

8. 완료 체크리스트와 인수

  • □ 승인된 7개 핵심 화면의 디자인과 역할별 흐름을 적용했다.
  • □ 로그인·기타 관리자 화면에서도 디자인이 일관되며 기존 메뉴가 유지된다.
  • □ 실제 데이터와 기존 API를 연결했고, 예시 수치·응답·연결 상태를 제거했다.
  • □ 교사와 관리자 권한, 공개·내부 정보의 경계가 유지된다.
  • □ 모바일·다크 모드·긴 콘텐츠·키보드·오류 상태를 확인했다.
  • □ 영향 검사와 최종 회귀 검사 결과를 PR에 기록했다.
  • □ 핵심 화면 전후 비교와 시안 대비 합리적인 차이를 설명했다.
  • □ 데이터·AI 실행 정책·인증 동작에 의도하지 않은 변경이 없다.
  • □ 배포 대상과 이전 정상 커밋을 기록했다. 문제 발생 시 변경 커밋 되돌리기 또는 이전 버전 재배포로 복구할 수 있다.
